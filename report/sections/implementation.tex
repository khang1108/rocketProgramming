\subsection{Common layer: chuẩn hóa giao tiếp và tiện ích dùng chung}

\subsubsection{Socket wrapper và mô hình lỗi}

Thay vì gọi trực tiếp POSIX/WinSock API, hệ thống xây dựng lớp \code{Socket} như một ``adapter'' thống nhất cho TCP/UDP. Lớp này đóng gói các thao tác then chốt: \code{bind()/listen()/accept()} cho TCP server, \code{connect()} cho TCP client, \code{send()/recv()} cho RTSP qua TCP, và \code{sendTo()/recvFrom()} cho RTP qua UDP. Điểm quan trọng là lớp \code{Socket} chủ động chuyển các lỗi hệ thống về exception ở mức C++ (\code{SocketException}, \code{SocketTimeout}), giúp code xử lý luồng điều khiển rõ ràng hơn (đặc biệt trong vòng lặp nhận RTP).

\begin{lstlisting}[language=C++, caption={Vòng lặp \texttt{send()} đảm bảo gửi đủ dữ liệu RTSP qua TCP}, label={lst:socket_send_all}]
int Socket::send(const uint8_t* data, size_t length) {
    size_t totalSent = 0;
    while (totalSent < length) {
        int bytes = ::send(sockfd_, (const char*)(data + totalSent),
                           length - totalSent, 0);
        if (bytes == SOCKET_ERROR) {
            // map error -> SocketTimeout / SocketException
            ...
        }
        totalSent += bytes;
    }
    return (int)totalSent;
}
\end{lstlisting}

Với RTP (UDP), socket được đặt timeout ngắn để thread nhận không bị block vĩnh viễn và có thể thoát khi \code{running\_} chuyển trạng thái.

\begin{lstlisting}[language=C++, caption={Nhận RTP với timeout để kiểm tra cờ dừng định kỳ}, label={lst:rtp_receiver_timeout}]
socket_->setTimeout(5);  // milliseconds (UDP)
...
try {
    int bytes = socket_->recvFrom(buffer, sizeof(buffer), senderAddr);
    ...
} catch (const SocketTimeout&) {
    continue;  // loop again to check running_
}
\end{lstlisting}

\subsubsection{RTSPMessage: parse/build theo định dạng dòng}

Thay vì parse ``thủ công'' rải rác, hệ thống gom chuẩn hóa RTSP ở lớp \code{RTSPMessage}. Lớp này cung cấp:
(1) \code{buildRequest/buildResponse} để sinh chuỗi RTSP chuẩn CRLF,
(2) \code{parseRequest/parseResponse} để tách request line/status line và headers vào \code{std::map},
(3) quy ước đọc \code{CSeq} thành số nguyên để dùng trực tiếp.

\begin{lstlisting}[language=C++, caption={Sinh request RTSP chuẩn CRLF và header CSeq}, label={lst:rtsp_build_request}]
std::string RTSPMessage::buildRequest(const std::string& method,
                                      const std::string url,
                                      int cseq,
                                      const std::map<std::string,std::string>& headers) {
    std::stringstream ss;
    ss << method << " " << url << " RTSP/1.0\r\n";
    ss << "CSeq: " << cseq << "\r\n";
    for (const auto& pair : headers) ss << pair.first << ": " << pair.second << "\r\n";
    ss << "\r\n";
    return ss.str();
}
\end{lstlisting}

\subsubsection{RTPPacket và xử lý wrap-around sequence number}

\code{RTPPacket} hiện thực header RTP (version, marker, payload type, sequence number, timestamp, SSRC) và payload. Một điểm dễ sai trong RTP là \textbf{sequence number 16-bit} sẽ wrap-around; vì vậy project bổ sung hàm \code{sequenceDifference()} để đo khoảng cách sequence theo modulo $2^{16}$, phục vụ thống kê mất gói ở Client và kiểm soát thứ tự ở Reassembler.

\begin{lstlisting}[language=C++, caption={Tính chênh lệch sequence theo modulo để xử lý wrap-around}, label={lst:seq_diff}]
int32_t RTPPacket::sequenceDifference(uint16_t seq1, uint16_t seq2) {
    int32_t diff = (int32_t)seq1 - (int32_t)seq2;
    if (diff > 32768)  diff -= 65536;
    if (diff < -32768) diff += 65536;
    return diff;
}
\end{lstlisting}

\subsubsection{Builder pattern cho RTPPacket}

Để giảm lỗi khi dựng packet và tăng tính ``self-documenting'', hệ thống sử dụng Builder pattern: \code{RTPPacketBuilder} yêu cầu set các trường bắt buộc (\code{sequenceNumber/timestamp/ssrc/payload}) trước khi \code{build()}. Nếu thiếu trường, builder ném \code{std::runtime\_error} để fail-fast ngay tại nơi tạo packet.

\begin{lstlisting}[language=C++, caption={Builder kiểm tra các trường bắt buộc trước khi build RTP packet}, label={lst:rtp_builder_validate}]
RTPPacket RTPPacketBuilder::build() {
    if (!seqSet_)       throw std::runtime_error("Sequence number not set");
    if (!timestampSet_) throw std::runtime_error("Timestamp not set");
    if (!ssrcSet_)      throw std::runtime_error("SSRC not set");
    if (!payloadSet_)   throw std::runtime_error("Payload not set");
    RTPPacket packet;
    packet.setSequenceNumber(sequenceNumber_);
    packet.setTimestamp(timestamp_);
    packet.setSSRC(ssrc_);
    packet.setPayload(payload_);
    packet.encode();  // serialize header -> raw bytes
    return packet;
}
\end{lstlisting}

\subsection{Server: RTSP state machine và luồng streaming RTP}

\subsubsection{Mô hình đa luồng và quản lý session}

\code{RTSPServer} chạy vòng lặp \code{accept()} trên TCP listen socket. Mỗi kết nối mới được gán \code{clientId}, tạo một \code{ServerWorker} và chạy nó trên một \code{std::thread} riêng. Danh sách session được bảo vệ bởi \code{std::mutex} để tránh race khi stop server.

\begin{lstlisting}[language=C++, caption={Tạo thread cho từng client trong \texttt{RTSPServer::run()}}, label={lst:server_accept}]
while (running) {
    std::unique_ptr<Socket> clientSocket = listenSocket->accept();
    ClientSession session;
    session.clientId = nextClientId++;
    session.worker = std::make_unique<ServerWorker>(session.clientId, std::move(clientSocket));
    session.workerThread = std::thread(&ServerWorker::run, session.worker.get());
    activeSession.push_back(std::move(session));
}
\end{lstlisting}

\subsubsection{ServerWorker: RTSP state machine và phân phối handler}

Mỗi \code{ServerWorker} duy trì state nội bộ \code{INIT/READY/PLAYING/PAUSED}. Vòng lặp \code{handleRtspRequests()} nhận request RTSP, parse, sau đó dispatch sang \code{handleSetup/handlePlay/handlePause/handleTeardown}. Việc tách handler giúp mỗi lệnh RTSP có phạm vi trách nhiệm rõ ràng (validate session, đổi state, start/stop thread streaming).

\begin{lstlisting}[language=C++, caption={Dispatch lệnh RTSP theo method ở ServerWorker}, label={lst:server_dispatch}]
auto request = RTSPMessage::parseRequest(msg);
if (request.method == "SETUP")    response = handleSetup(request);
else if (request.method == "PLAY")     response = handlePlay(request);
else if (request.method == "PAUSE")    response = handlePause(request);
else if (request.method == "TEARDOWN") response = handleTeardown(request);
else response = RTSPMessage::buildResponse(400, "Bad Request", request.cseq);
\end{lstlisting}

\textbf{Lý do thiết kế State Machine:} Máy trạng thái giúp hệ thống có thể kiểm tra tính hợp lệ của mỗi request dựa trên trạng thái hiện tại. Ví dụ, nếu Client gửi PLAY khi đang ở trạng thái INIT (chưa SETUP), Server sẽ trả về lỗi \texttt{455 Method Not Valid in This State}. Điều này đảm bảo tính nhất quán của giao thức và tránh các hành vi không xác định.

\begin{lstlisting}[language=C++, caption={Validation state trước khi xử lý PLAY request}, label={lst:state_validation}]
std::string ServerWorker::handlePlay(const RTSPRequest& request) {
    if (state_ != State::READY && state_ != State::PAUSED) {
        return RTSPMessage::buildResponse(455, "Method Not Valid in This State", 
                                         request.cseq);
    }
    // ... proceed with PLAY logic
    state_ = State::PLAYING;
    return RTSPMessage::buildResponse(200, "OK", request.cseq, headers);
}
\end{lstlisting}

\textbf{Giải thích chi tiết các bước:}

\begin{enumerate}
\item \textbf{SETUP phase:} Client gửi cổng UDP mà nó sẽ lắng nghe RTP (ví dụ: 25000) trong header \texttt{Transport}. Server phản hồi với \texttt{Session ID} (dùng để nhận diện phiên này trong các request sau) và cổng UDP của Server. Đây là bước chuẩn bị tài nguyên.

\item \textbf{PLAY phase:} Client gửi PLAY kèm Session ID. Server khởi động background thread để đọc video file, encode thành RTP packets và gửi qua UDP. Lưu ý rằng RTSP response trả về ngay lập tức, không đợi streaming loop chạy.

\item \textbf{RTP streaming:} Luồng dữ liệu RTP chảy độc lập qua UDP, không có acknowledgment. Đây là điểm khác biệt quan trọng: control plane (RTSP/TCP) và data plane (RTP/UDP) tách biệt hoàn toàn.

\item \textbf{PAUSE:} Dừng streaming loop nhưng không giải phóng session. Client có thể gửi PLAY lại để tiếp tục từ frame hiện tại.

\item \textbf{TEARDOWN:} Dọn dẹp hoàn toàn, đóng socket UDP, giải phóng Session ID. Client cần SETUP lại nếu muốn xem tiếp.
\end{enumerate}

\subsubsection{Streaming loop: điều phối FPS, đọc frame, encode và gửi UDP}

Khi nhận PLAY hợp lệ, Worker khởi động một background thread chạy \code{streamingLoop()}. Vòng lặp này có ba bước trọng tâm: (1) đọc frame từ \code{VideoStream}, (2) encode frame thành một hoặc nhiều RTP packet (Strategy), (3) gửi packet qua UDP tới \code{clientIP\_ : clientRTPPort\_}. \code{Timer} được dùng để kiểm soát nhịp gửi theo interval.

\begin{lstlisting}[language=C++, caption={Luồng streaming: đọc frame, encode RTP và gửi UDP}, label={lst:streaming_loop}]
while (streaming_) {
    frameTimer_->start();

    std::vector<uint8_t> frame = videoStream_->nextFrame();
    auto packets = encodingStrategy_->encode(frame, sequenceNumber_, timestamp_, ssrc_);

    for (auto& packet : packets) {
        socket_->sendTo(packet.getPacketVector().data(), packet.getLength(),
                        clientIP_, clientRTPPort_);
        sequenceNumber_ = packet.getSequenceNumber() + 1;
    }

    timestamp_ += 3600;   // advance timestamp per frame (project convention)
    frameTimer_->wait();
}
\end{lstlisting}

\textbf{Giải thích chi tiết thuật toán:}

\paragraph{Bước 1 - Kiểm tra cờ streaming\_:} Đây là atomic boolean cho phép thread chính dừng loop từ bên ngoài (khi nhận PAUSE hoặc TEARDOWN). Việc kiểm tra ở đầu loop đảm bảo thread có thể thoát ngay lập tức.

\paragraph{Bước 2 - Timer.start():} Ghi nhận thời điểm bắt đầu xử lý frame. Timer sử dụng \texttt{std::chrono::high\_resolution\_clock} để đo thời gian chính xác. Đây là điểm bắt đầu của "budget thời gian" cho frame này.

\paragraph{Bước 3 - Đọc frame từ VideoStream:} \texttt{VideoStream} scan file MJPEG để tìm marker SOI/EOI (sẽ giải thích chi tiết ở phần sau). Nếu hết video, \texttt{nextFrame()} có thể trả về frame rỗng hoặc loop lại từ đầu (tùy cấu hình).

\paragraph{Bước 4 - Encode frame thành RTP packets:} Strategy pattern được áp dụng tại đây. \texttt{EncodingStrategy} nhận frame (có thể lớn tới vài trăm KB), chia thành nhiều fragments nếu cần, và wrap mỗi fragment vào RTP packet với sequence number tăng dần.

\paragraph{Bước 5 - Gửi tất cả packets qua UDP:} Vòng lặp đi qua từng packet và gọi \texttt{sendTo()} với địa chỉ \texttt{clientIP:clientRTPPort}. UDP không đảm bảo thứ tự hay độ tin cậy, nhưng đổi lại có độ trễ thấp. Sequence number trong RTP header sẽ giúp Client sắp xếp lại.

\paragraph{Bước 6 - Tăng timestamp:} Timestamp trong RTP không phải là wall-clock time, mà là "media time". Dự án sử dụng convention \texttt{timestamp += 3600} mỗi frame (tương ứng với 90kHz clock rate của RTP, chia cho 25 FPS). Điều này giúp Client biết khoảng cách thời gian giữa các frame.

\paragraph{Bước 7 - Timer.wait():} Đây là bước quan trọng nhất để kiểm soát FPS. Timer tính toán thời gian đã dùng (từ start() đến wait()) và sleep phần còn lại để đạt interval mục tiêu (ví dụ: 40ms cho 25 FPS). Nếu xử lý frame mất quá lâu (> 40ms), \texttt{wait()} sẽ return ngay lập tức mà không sleep, tránh "nợ" thời gian tích lũy.

\begin{lstlisting}[language=C++, caption={Timer.wait() chỉ sleep phần thời gian còn lại của interval}, label={lst:timer_wait_logic}]
void Timer::wait() {
    auto now = std::chrono::high_resolution_clock::now();
    auto elapsed = std::chrono::duration_cast<std::chrono::milliseconds>(now - startTime_);
    auto remaining = std::chrono::milliseconds(intervalMs_) - elapsed;
    
    if (remaining.count() > 0) {
        std::this_thread::sleep_for(remaining);
    }
    // else: frame processing took too long, skip sleep
}
\end{lstlisting}

\textbf{Tại sao thiết kế như vậy?} Cách tiếp cận "budget-based timing" này đảm bảo:
\begin{itemize}
\item FPS ổn định ngay cả khi thời gian xử lý biến động
\item Không tích lũy lag khi một frame xử lý chậm (skip sleep thay vì queue up delay)
\item Client nhận được luồng video với bitrate dự đoán được, giúp buffer hoạt động hiệu quả
\end{itemize}

\subsubsection{Strategy pattern: SD vs HD và phân mảnh payload}

Với video MJPEG, kích thước frame có thể vượt MTU. Để tránh UDP fragmentation ở tầng IP, hệ thống giới hạn \code{MAX\_PAYLOAD\_SIZE} (1400 bytes) và tự phân mảnh ở tầng RTP. Strategy pattern được dùng để tách logic encode: \code{SDEncodingStrategy} gửi một packet/1 frame (chỉ phù hợp frame nhỏ), còn \code{HDEncodingStrategy} chia frame thành nhiều packet, dùng marker bit để đánh dấu fragment cuối.

\begin{lstlisting}[language=C++, caption={HD encoding: chia frame thành nhiều RTP packet và set marker cho fragment cuối}, label={lst:hd_fragment}]
while (offset < frameData.size()) {
    size_t chunk = std::min((size_t)RTPPacket::MAX_PAYLOAD_SIZE,
                            frameData.size() - offset);
    bool isLast = (offset + chunk >= frameData.size());

    RTPPacket pkt = RTPPacketBuilder()
        .setSequenceNumber(seqNum++)
        .setTimestamp(timestamp)
        .setSSRC(ssrc)
        .setMarker(isLast ? 1 : 0)
        .setPayload(&frameData[offset], chunk)
        .build();

    packets.push_back(pkt);
    offset += chunk;
}
\end{lstlisting}

\subsubsection{Giải thích chi tiết về RTP Fragmentation: tại sao cần và cách hoạt động}

\textbf{Vấn đề MTU và IP Fragmentation:} Mạng Ethernet tiêu chuẩn có MTU (Maximum Transmission Unit) là 1500 bytes. Nếu gói UDP vượt quá MTU, tầng IP sẽ tự động phân mảnh (IP fragmentation). Tuy nhiên, với UDP, nếu \textit{bất kỳ} fragment nào bị mất, toàn bộ gói sẽ bị discard. Đối với video streaming, điều này không chấp nhận được.

\textbf{Giải pháp Application-Level Fragmentation:} Thay vì để IP phân mảnh, hệ thống chủ động chia frame thành nhiều RTP packets nhỏ hơn (mỗi packet $\leq$ 1400 bytes payload). Khi đó:
\begin{itemize}
\item Mỗi RTP packet đi trong một UDP datagram riêng, không bị phân mảnh ở tầng IP
\item Nếu một packet bị mất, Client vẫn có thể nhận các packets khác của cùng frame
\item Với MJPEG, việc mất một phần frame chỉ gây méo hình một phần, vẫn hiển thị được (graceful degradation)
\end{itemize}

\subsubsection{VideoStream: thuật toán trích xuất frame MJPEG bằng marker JPEG}

File \code{.Mjpeg} trong project là chuỗi các ảnh JPEG nối tiếp. Để trích xuất frame, \code{VideoStream} đọc file vào buffer và tìm cặp marker JPEG: SOI \code{0xFF 0xD8} (Start Of Image) và EOI \code{0xFF 0xD9} (End Of Image). Khi tìm được EOI, lớp này cắt đoạn byte tương ứng và trả về như một frame hoàn chỉnh.

\begin{lstlisting}[language=C++, caption={Quét marker JPEG SOI/EOI để cắt frame trong \texttt{VideoStream::nextFrame()}}, label={lst:videostream_markers}]
while (file_.read((char*)&byte, 1)) {
    buffer_.push_back(byte);

    if (buffer_.size() >= 2) {
        uint8_t b1 = buffer_[buffer_.size()-2];
        uint8_t b2 = buffer_[buffer_.size()-1];

        if (!inFrame && b1 == 0xFF && b2 == 0xD8) {
            inFrame = true; frameStart = buffer_.size() - 2;
        }
        if (inFrame && b1 == 0xFF && b2 == 0xD9) {
            size_t frameEnd = buffer_.size();
            std::vector<uint8_t> frame(buffer_.begin()+frameStart, buffer_.begin()+frameEnd);
            buffer_.erase(buffer_.begin(), buffer_.begin()+frameEnd);
            return frame;
        }
    }
}
\end{lstlisting}

Thuật toán này dựa trên cấu trúc của định dạng JPEG: mỗi ảnh JPEG bắt đầu bằng marker SOI (Start Of Image: \texttt{0xFF 0xD8}) và kết thúc bằng EOI (End Of Image: \texttt{0xFF 0xD9}). File \texttt{.Mjpeg} chỉ đơn giản là nhiều ảnh JPEG nối tiếp nhau mà không có delimiter hay header đặc biệt.

\textbf{Giải thích chi tiết thuật toán:}

\paragraph{Tại sao cần buffer tích lũy?} Không thể đọc từng ảnh JPEG một cách trực tiếp vì không biết trước kích thước của mỗi ảnh. Thuật toán phải scan tuần tự để tìm marker. Buffer (\texttt{std::vector<uint8\_t>}) tích lũy bytes cho đến khi phát hiện được một frame hoàn chỉnh.

\paragraph{Phát hiện SOI:} Khi gặp \texttt{0xFF 0xD8}, đánh dấu \texttt{inFrame = true} và ghi nhận vị trí \texttt{frameStart}. Điều này cho biết "từ đây trở đi là dữ liệu của một frame".

\paragraph{Phát hiện EOI:} Khi gặp \texttt{0xFF 0xD9} VÀ \texttt{inFrame == true}, ta biết frame đã hoàn chỉnh. Lúc này extract đoạn \texttt{[frameStart, currentPos]} từ buffer, xóa phần đã extract để tiết kiệm bộ nhớ, và return frame.

\paragraph{Xử lý khi hết file:} Nếu đọc hết file mà chưa tìm thấy EOI (có thể do file corrupt hoặc frame cuối bị cắt), trả về frame rỗng. Điều này khiến streaming loop có thể phát hiện end-of-stream.

\paragraph{Tối ưu hóa bộ nhớ:} Sau khi extract frame, thuật toán xóa phần đã dùng khỏi buffer bằng \texttt{buffer\_.erase()}. Điều này quan trọng vì video file có thể có hàng nghìn frames; nếu không xóa, buffer sẽ phình to không kiểm soát.

\subsection{Client: RTSP điều khiển, nhận RTP, ghép frame và buffer/cache}

\subsubsection{RTSPClient: phiên điều khiển và cơ chế ``restart''}

\code{RTSPClient} chịu trách nhiệm tạo kết nối TCP đến server, gửi các request RTSP (SETUP/PLAY/PAUSE/TEARDOWN), và parse response để lấy \code{Session} ID. Với yêu cầu ``replay'' sau khi hết video, client hỗ trợ cơ chế restart bằng header \code{Restart: true} trong PLAY; server kiểm tra header này để reset \code{VideoStream} về đầu file.

\begin{lstlisting}[language=C++, caption={Client gửi PLAY kèm header Restart khi cần phát lại}, label={lst:client_play_restart}]
std::map<std::string,std::string> headers;
headers["Session"] = sessionId_;
if (restart) headers["Restart"] = "true";

std::string request = RTSPMessage::buildRequest("PLAY", rtspUri_, cseq_, headers);
socket_->send((const uint8_t*)request.c_str(), request.size());
\end{lstlisting}

\subsubsection{RTPReceiver: nhận UDP và thống kê mất gói}

\code{RTPReceiver} chạy background thread \code{receiveLoop()} để nhận packet và chuyển cho \code{FrameReassembler}. Đồng thời, receiver cập nhật thống kê loss dựa trên chênh lệch sequence; phần này dựa trực tiếp trên \code{RTPPacket::sequenceDifference()} để xử lý wrap-around.

\begin{lstlisting}[language=C++, caption={Tính packet loss dựa trên chênh lệch sequence}, label={lst:client_loss_stats}]
int32_t diff = RTPPacket::sequenceDifference(currentSeq, lastSequenceNumber_);
if (diff > 1) {
    packetLost_ += static_cast<uint64_t>(diff - 1);
}
lastSequenceNumber_ = currentSeq;
\end{lstlisting}

\subsubsection{Giải thích chi tiết RTP Sequence Number Wrap-around}

Trước khi đi vào thuật toán reassembly, cần hiểu rõ vấn đề wrap-around của sequence number. RTP sử dụng sequence number 16-bit, có nghĩa là sau 65535 packets, nó sẽ quay về 0. Điều này gây ra vấn đề khi so sánh thứ tự:

Đoạn mã dưới đây minh hoạ phép so sánh trực tiếp bị sai khi sequence wrap-around.

\begin{lstlisting}[language=C++, caption={Wrap-around: so sánh trực tiếp bị sai}, label={lst:wraparound_problem}]
uint16_t seq1 = 65535;  // sent earlier
uint16_t seq2 = 0;      // sent later after wrap
if (seq1 < seq2) { /* ... */ }
\end{lstlisting}

Công thức tính khoảng cách sequence đúng:

\begin{lstlisting}[language=C++, caption={sequenceDifference function handles wrap-around correctly}, label={lst:seq_diff_correct}]
int32_t RTPPacket::sequenceDifference(uint16_t seq1, uint16_t seq2) {
    int32_t diff = (int32_t)seq1 - (int32_t)seq2;
    
    // If diff > 32768, seq2 has wrapped past 0 and is greater than seq1
    // Example: seq1=100, seq2=65000 -> diff=100-65000=-64900
    // Actually seq2 is older, distance = -64900 + 65536 = 636
    if (diff > 32768)  diff -= 65536;
    
    // If diff < -32768, seq1 has wrapped past 0 and is greater than seq2
    // Example: seq1=65000, seq2=100 -> diff=65000-100=64900
    // Actually seq1 is older, distance = 64900 - 65536 = -636
    if (diff < -32768) diff += 65536;
    
    return diff;
}
\end{lstlisting}

\textbf{Ứng dụng trong phát hiện packet loss:}

\begin{lstlisting}[language=C++, caption={Calculate packet loss correctly with wrap-around}, label={lst:loss_with_wraparound}]
int32_t diff = RTPPacket::sequenceDifference(currentSeq, lastSeq);
if (diff > 1) {
    // Example: lastSeq=65534, currentSeq=2
    // diff = sequenceDifference(2, 65534)
    //      = 2 - 65534 = -65532
    //      = -65532 + 65536 = 4
    // Lost packets = 4 - 1 = 3 (packets 65535, 0, 1)
    packetLost_ += (diff - 1);
}
\end{lstlisting}

\subsubsection{FrameReassembler: thuật toán ghép fragment phức tạp với xử lý out-of-order}

Đối với HD mode, một frame có thể gồm nhiều RTP packet. \code{FrameReassembler} gom các fragment theo \code{timestamp}, sắp thứ tự theo \code{sequenceNumber}, và xác định điểm kết thúc frame dựa trên marker bit. Khi frame hoàn chỉnh, reassembler nối payload và push vào \code{FrameBuffer}. Để tránh leak khi mất marker (mất gói), module cũng hỗ trợ giới hạn bộ nhớ cho map và chiến lược ``flush'' khi đổi timestamp.

\begin{lstlisting}[language=C++, caption={Ghép frame khi gặp marker bit và đẩy vào buffer}, label={lst:reassemble_marker}]
if (packet.getMarker() == 1) {
    auto& fragments = frameFragments_[timestamp];
    std::sort(fragments.begin(), fragments.end(),
              [](auto& a, auto& b){ return a.getSequenceNumber() < b.getSequenceNumber(); });

    std::vector<uint8_t> frameData;
    for (auto& frag : fragments) {
        const auto& payload = frag.getPayload();
        frameData.insert(frameData.end(), payload.begin(), payload.end());
    }

    frameBuffer_->push(frameData);
    frameFragments_.erase(timestamp);
}
\end{lstlisting}

\textbf{Giải thích chi tiết các bước quan trọng:}

\paragraph{Bước 1 - Nhóm theo timestamp:} Tất cả fragments của cùng một frame có cùng RTP timestamp. Reassembler dùng cấu trúc \texttt{std::map} với key là \texttt{uint32\_t} timestamp và value là \texttt{std::vector<RTPPacket>} để nhóm. Mỗi entry trong map chứa danh sách packets chưa sắp xếp của một frame.

\paragraph{Bước 2 - Kiểm tra marker bit:} Chỉ khi nhận được packet có \texttt{marker=1}, reassembler mới biết "frame này đã hoàn chỉnh (ít nhất về mặt gửi)". Trước đó, các fragments chỉ được tích lũy mà không xử lý.

\paragraph{Bước 3 - Sắp xếp theo sequence number:} Do UDP không đảm bảo thứ tự, các fragments có thể đến lung tung. Thuật toán sort theo sequence để ghép đúng thứ tự. Đây là lúc hàm \texttt{sequenceDifference()} quan trọng để so sánh chính xác.

\begin{lstlisting}[language=C++, caption={Sort fragments handling wrap-around}, label={lst:sort_fragments}]
std::sort(fragments.begin(), fragments.end(),
    [](const RTPPacket& a, const RTPPacket& b) {
        // Cannot use a.seq < b.seq due to wrap-around
        // Use sequenceDifference for correct comparison
        return RTPPacket::sequenceDifference(a.getSequenceNumber(), 
                                             b.getSequenceNumber()) < 0;
    });
\end{lstlisting}

\paragraph{Bước 4 - Concatenate payloads:} Sau khi sort, nối tất cả payloads thành một \texttt{std::vector<uint8\_t>} duy nhất. Đây chính là dữ liệu JPEG hoàn chỉnh.

\paragraph{Bước 5 - Validation:} Kiểm tra \texttt{frameData} không rỗng và có thể decode được (optional: có thể check JPEG header \texttt{0xFF 0xD8}). Nếu invalid (có thể do mất quá nhiều fragments), discard frame.

\paragraph{Bước 6 - Push vào FrameBuffer và cleanup:} Frame hoàn chỉnh được đẩy vào buffer thread-safe. Sau đó xóa entry trong \texttt{fragments} map để giải phóng bộ nhớ. Điều này quan trọng vì nếu không xóa, map sẽ phình to với các frames cũ.

\textbf{Xử lý edge cases:}

\begin{itemize}
\item \textbf{Mất marker packet:} Nếu packet cuối (có marker) bị mất, frame sẽ không bao giờ được reassemble. Để tránh leak memory, hệ thống có thể implement timeout: nếu một timestamp không nhận thêm packet sau X giây, force flush hoặc discard.

\item \textbf{Packets đến muộn:} Nếu packet có timestamp cũ đến sau khi frame đó đã được reassemble (entry đã bị erase), packet sẽ bị ignore. Đây là trade-off giữa latency và completeness.

\item \textbf{Out-of-order severe:} Nếu packet có sequence number quá xa so với các packets khác của cùng timestamp, có thể là lỗi. Code có thể log warning để debug.
\end{itemize}

\subsubsection{FrameBuffer: buffer như một ``video cache'' thread-safe}

\code{FrameBuffer} là lớp trung gian quan trọng nhất để ``hấp thụ jitter'' mạng. Nó được hiện thực như một hàng đợi thread-safe, với \code{push()} từ thread nhận RTP và \code{tryPop()} từ UI thread. \code{std::mutex} và \code{std::condition\_variable} được dùng để đồng bộ; \code{close()} đảm bảo thread consumer không bị kẹt khi shutdown.

\begin{lstlisting}[language=C++, caption={FrameBuffer đồng bộ bằng mutex + condition variable}, label={lst:framebuffer_push_pop}]
void FrameBuffer::push(const std::vector<uint8_t>& frame) {
    std::unique_lock<std::mutex> lock(mtx_);
    if (closed_) return;
    buffer_.push_back(frame);
    cv_.notify_one();
}

bool FrameBuffer::tryPop(std::vector<uint8_t>& frame) {
    std::unique_lock<std::mutex> lock(mtx_);
    if (buffer_.empty()) return false;
    frame = std::move(buffer_.front());
    buffer_.pop_front();
    return true;
}
\end{lstlisting}

\subsubsection{FrameBuffer: vai trò như video cache và cơ chế Producer-Consumer}

\textbf{Tại sao cần FrameBuffer?} Nếu UI render frame ngay khi nhận được từ mạng, video sẽ giật liên tục do jitter mạng. FrameBuffer đóng vai trò như một "bể chứa" (reservoir) để:
\begin{itemize}
\item Tách nhịp nhận mạng (bursty, không đều) khỏi nhịp hiển thị (đều đặn 25 FPS)
\item Hấp thụ jitter: khi mạng chậm, buffer cung cấp frames từ dự trữ
\item Cho phép prebuffering để tránh underrun ngay từ đầu
\end{itemize}

\subsubsection{ClientUI (Qt): prebuffer, adaptive playback và cơ chế chống jitter}

Ở phía UI, state machine được đơn giản hóa thành \code{INIT/READY/PLAYING}. Đồng thời, UI điều chỉnh interval của \code{frameTimer\_} theo kích thước buffer để tránh tiêu thụ hết buffer khi mạng chậm.

\textbf{Giải thích chi tiết cơ chế Prebuffering:}

Prebuffering là kỹ thuật "trả độ trễ để lấy ổn định". Thay vì phát ngay khi nhận được frame đầu tiên, Client đợi cho đến khi tích lũy đủ \texttt{PREBUFFER\_FRAMES} (ví dụ: 50 frames $\approx$ 2 giây ở 25 FPS). Lý do:

\begin{itemize}
\item \textbf{Khởi động ổn định:} Vài frame đầu có thể đến chậm do TCP slow start, DNS lookup, etc. Nếu phát ngay, buffer sẽ cạn trong vài giây đầu.
\item \textbf{Chống jitter đầu phát:} Tạo "vùng đệm dự phòng" để hấp thụ biến động mạng trong giai đoạn đầu.
\item \textbf{User experience:} Người dùng thích chờ 2 giây để load rồi xem mượt hơn là xem giật liên tục.
\end{itemize}

\textbf{Tại sao không giữ cố định 25 FPS?} Nếu render cố định 40ms/frame nhưng mạng chỉ cung cấp trung bình 45ms/frame (do bandwidth thấp), buffer sẽ cạn dần và video sẽ giật. Adaptive timer "nhượng bộ" bằng cách giảm FPS xuống 20-22 để buffer có thể hồi phục.

\textbf{Tại sao không tăng interval lên cao hơn (ví dụ 100ms)?} Vì điều đó làm video quá chậm (10 FPS) và không còn watchable. 20 FPS là ngưỡng thấp nhất mà con người vẫn cảm nhận được chuyển động tương đối mượt.

\begin{lstlisting}[language=C++, caption={Adaptive interval logic in UI timer callback}, label={lst:adaptive_detailed}]
void ClientUI::onRenderFrame() {
    size_t bufferSize = frameBuffer_->size();
    
    // If buffer is completely empty, trigger rebuffering
    if (bufferSize == 0) {
        prebufferReady_ = false;  // return to buffering state
        return;
    }
    
    // Adjust interval based on buffer level
    if (bufferSize >= 20)      frameTimer_->setInterval(38);  // 26.3 FPS
    else if (bufferSize >= 10) frameTimer_->setInterval(40);  // 25 FPS
    else if (bufferSize >= 5)  frameTimer_->setInterval(45);  // 22.2 FPS
    else                       frameTimer_->setInterval(50);  // 20 FPS
    
    // Render frame
    std::vector<uint8_t> frame;
    if (frameBuffer_->tryPop(frame)) {
        displayFrame(frame);
        currentFrame_++;
    }
}
\end{lstlisting}

\textbf{Kết quả của cơ chế này:} Video có thể tự động thích nghi với điều kiện mạng:
\begin{itemize}
\item Mạng tốt (> 25 FPS): buffer cao, render 26 FPS, smooth
\item Mạng trung bình (= 25 FPS): buffer ổn định, render 25 FPS
\item Mạng chậm (< 25 FPS): buffer giảm dần, render chậm xuống 20-22 FPS, vẫn xem được
\item Mạng rất chậm: buffer cạn, trigger rebuffering, chờ buffer đầy rồi tiếp tục
\end{itemize}

Timeline slider được mở rộng thành \code{BufferedSlider} để hiển thị vùng đã buffer (``buffered position''), tính bằng \code{currentFrame + bufferSize}. Phần vẽ bổ sung được hiện thực trong \code{paintEvent()}.

\subsection{Ghi nhận triển khai: logging, cấu hình và khả năng mở rộng}

Hệ thống sử dụng \code{Logger} (Singleton) để log đồng thời ra console và file, đảm bảo thread-safe bằng \code{std::mutex}. Việc cấu hình tách riêng ở \code{Config} (SingletonWithInit) cho phép thay đổi tham số runtime (port, video file, log level) mà không cần rebuild.

\begin{lstlisting}[language=C++, caption={Logger Singleton: log thread-safe và lọc theo mức}, label={lst:logger_singleton}]
void Logger::log(LogLevel level, const std::string& message) {
    std::lock_guard<std::mutex> lock(mutex_);
    if (!initialized_ || level < minLevel_) return;
    std::cout << "[" << getCurrentTime() << "] [" << levelToString(level) << "] "
              << message << std::endl;
    if (logFile_.is_open()) logFile_ << ...;
}
\end{lstlisting}

Về khả năng mở rộng, các điểm đã ``cắm sẵn'' trong thiết kế gồm: Strategy cho encoding (thêm H.264/H.265 packetization), Builder cho các message phức tạp hơn, và RTSP state machine tách handler để bổ sung DESCRIBE/SET\_PARAMETER/RANGE trong tương lai mà không làm vỡ luồng chính.
